# ADR 0004: 图片访问 URL 与签名格式

## 状态
Accepted

## 背景

图片访问 URL 原先形如 `image?path=<relPath>&t=<mtime>&s=<size>&w=<width>&sig=<sig>`，
签名只覆盖 `path|t|s|w|raw` 这几个**已知参数的值**。这带来两个问题：

1. **未知参数被静默忽略**。handler 对签名之外的参数不做任何检查，只靠逐个显式拒绝
   （如 `fmt`、`q`）来兜底——每新增一个废弃参数就要加一条 400 分支，漏掉一条就失去约束。
2. **签名与消费的粒度不一致**。`raw` 按「值」签名（`params.Get`）却按「存在性」消费
   （`query.Has`），而二者在 `Get` 语义下不可区分：对合法 URL 追加空值 `raw=` 即可让签名
   仍然通过、却让 handler 切换为原图直出。实测确认该绕过成立。

根因是「签名覆盖一组已知键」这一模型本身：它要求调用方与校验方对**参数集合**保持一致，
任何一侧增删都会产生缝隙。改为「签名覆盖整段字符串」可消除该模型，无需维护键集合。

## 决定

**URL 形如 `/image/<sig>/<relPath>?<params>`，签名覆盖 `/image/<sig>` 之后那个 `/` 起的整个字符串。**

- **签名对象**：`<escapedRelPath>[?<rawQuery>]`，逐字节。参数是否存在、取值、顺序、
  `?a` 与 `?a=` 的区别都在签名内，因此**不需要参数白名单**：任何未参与生成的改动
  （含未知参数）都会导致验签失败。
- **`sig` 位于路径段**，使「被签名的字符串」与「签名之后的部分」重合，无需另行约定参数顺序。
  编码用 `base64.RawURLEncoding`（无 `=` 填充），避免 `=` 在中间件/代理中被特殊处理。
- **路径逐段转义**（`url.PathEscape` 后以 `/` 重连）而非整体转义，否则路径分隔符会编码成
  `%2F`，多级路径塌成一段。
- **验签必须读取 `r.RequestURI`**（线路原始目标串）。理由：`url.URL.Path` 已解码，无法区分
  `%2F` 与 `/`；`EscapedPath()` 在 `RawPath` 失效时**重新编码**，丢原始字形；
  `url.Values.Encode()` 会把 `%20` 改写为 `+` 并丢失参数顺序与 `?a` / `?a=` 的区别。
  absolute-form（代理转发）做最小归一，仅剥离 scheme 与 host。
- **路由用 `PathPrefix("/image/")`**，不使用 `mux.Vars`：其值为解码后结果，
  `a%2Fb` 与 `a/b` 不可区分，不能作为验签输入。保留 mux 默认的 `cleanPath`——
  含 `.`/`..` 的路径会在进入 handler 前被 301，而重定向目标仍带原签名，跟随必然验签失败
  （fail closed），是免费的第一道防线。裸 `/image` 另行注册到同一 handler：
  前缀路由不匹配它，若不注册会落入 SPA catch-all 而返回 200 HTML；交给 handler 则按
  「格式残缺」返回 403。
- **载荷中「首个 `?` 之前即路径」**：该约定成立的前提是签发侧对路径逐段转义，
  因而文件名里的 `?` 已被编码为 `%3F`，不可能与查询串分隔符混淆。
  absolute-form（代理转发）通过按分隔符**原样切片**剥离 scheme 与 authority，
  不经 `url.URL` 重建。
- **`t`/`s` 保留在查询串中**。它们不是缓存优化，而是**图片身份的一部分**：
  领域层的图片 ID 即 `img:<modTime.UnixNano()>:<relPath>`，同路径文件被替换（修改时间或大小
  变化）后就是另一张图片，其 URL 必须随之失效。是否与磁盘现状比对不在本 ADR 范围。
- **移除非签名参数的显式 400 白名单**（原 `fmt`、`q` 分支）。既然未参与生成的参数必然验签失败，
  逐个拒绝既是冗余又易漏。`raw` 与 `width` 同时出现的 400 **保留**：那是两个已签名参数之间的
  语义矛盾（原图 vs 宽高变体），属生成侧错误，静默取舍会掩盖 bug。
- **验签前置于一切响应分支，包括 304 短路**。`/image` 无登录态，签名是其唯一信任边界。
- **签发侧与验证侧都做根目录围栏**。签名不覆盖「目标是否在根目录内」这一属性，
  且 `toRelativePath` 原先在 `filepath.Rel` 出错时静默返回绝对路径。两侧分别：
  签发侧拒绝根外路径并让 `Rel` 失败报错；验证侧在验签后用既有的 `util.EnsurePathInRoot`
  复核。属纵深防御，不替代签名。
- **错误语义**：签名类失败（缺失、非法编码、不匹配、格式残缺）一律 403，不细分原因；
  路径不存在 404。
- **不兼容旧 URL**：旧格式全部失效，不做双格式共存。

## 后果

### 正面
- 新增参数无需改动验签逻辑，「未知参数」这一类别从模型中消失
- `raw` 的存在性与取值都被签名覆盖，前述绕过被构造性消除
- 签名与路径同为路径段，URL 结构更接近标准资源定位
- 补上了 `/image` 长期缺失的根目录围栏（此前仅依赖签名完整性）

### 负面
- 部署后旧 URL 全部失效，引发一次缓存未命中风暴（本地单用户应用，可接受；
  前端不持久化图片 URL，仅持久化 `useRawImage` 布尔值，影响面有限）
- 验签依赖 `RequestURI` 而非解析后的 URL，对调用方是更严格的约束
  （不可用 `url.URL` 重建目标串后验签）
- 含 `.`/`..` 的畸形请求会得到 301 而非 403，错误语义不完全统一

## 相关
- ADR 0003 记录了 `fmt` 与 `q` 两次契约收窄；本 ADR 消除了它们当时所需的显式 400 分支
