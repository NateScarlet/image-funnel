# 拉取式转码队列与 ffmpeg AVIF 编码

查看器在局域网快速切换（0.5 秒自动排除节奏）时卡顿：AVIF 全尺寸 4K 转码耗时约 2.2 秒（ImageMagick/libheif），且前端批量预载请求与用户当前查看请求在后端转码并发限制前平等竞争——切换瞬间当前图的请求可能排在多个陈旧预载之后。

## 考虑过的方案

- **服务端按 session 队列主动预热下一批图片** — 服务端需要猜测用户会请求哪个分辨率（由前端 zoom 决定），猜错即浪费转码；且只覆盖 session 视图，浏览视图无法受益。
- **预载 URL 加 prefetch 参数标记低优先级** — 预载的目的是预下载（拿到字节+解码），把预载请求本身降级会让预下载失效；且签名 URL 不允许前端追加参数。
- **保留 singleflight + 双固定队列（高/低两条车道）** — GET 走旁路时与预热任务可对同一张图双跑，只能靠 singleflight 兜底，"一张图占两个槽"；两条固定队列把"谁拿到释放的槽位"和"低优先级准入上限"两个关注点硬编码在一个结构里。
- **运行中取消已启动的转码进程** — 与"切到 N+1 时 abort 预载与 GET 到达"存在竞态窗口，取消太急会误杀马上要用的转码；需要引用计数 + 宽限期等补丁，复杂度不成比例。

## 结果

- **拉取式队列**：前端 HEAD 请求只是需求信号（登记"这张图现在有人要"），abort 即撤回；后端 worker 从需求队列**拉取**任务执行。等待者归零的未启动任务直接丢弃——队列内容永远追随最新需求，旧一批不会堵住新一批。
- **GET 也进队列**（高优先级）：同 key 去重收进队列本身，后到的 GET 搭乘进行中的同一转码；singleflight 装饰器删除。
- **专职高优先级 worker**：worker 池中 1 个只收高优先级任务且空闲不帮跑低优先级——用户查看请求永远有立即可用的执行槽位，等效于"低优先级最多占 N-1 槽"的槽位预留，但不引入并发 cap 概念。
- **缓存归应用层编排，处理器纯转码**：缓存命中完全不经过队列；magick 处理器剥离缓存依赖；变体 key（含编码器标识）由 coordinator 计算。
- **两阶段预载**：HEAD（登记需求）成功后 GET + decode 预下载，切换时缓存必命中。
- **ffmpeg/SVT-AV1 作为 AVIF 编码器**：启动时探测（实际编码一张 64×64 测试图验证链路；SVT-AV1 最小支持 4×4），失败日志警告并回退 ImageMagick；运行时不回退（快速失败——启动探测已证明环境可用，中途失败属异常状态）；WebP 路径保持 ImageMagick 不动；编码器标识进入变体缓存 key，回退切换不会误用另一编码器的产物。AVIF muxer 不支持不可寻址输出，编码结果经临时文件中转。
- **已启动的转码跑完入缓存**（即使需求全部撤回）：浪费有界（≤单张转码时长），且避免竞态窗口内误杀重启。
- **可强制回退 ImageMagick**：配置 `IMAGE_FUNNEL_IMAGE_PROCESSOR=magick` 跳过探测，所有转码
  走 ImageMagick；默认 `auto` 保持"探测可用则用 ffmpeg"的行为。填非法值启动即失败，避免
  拼写错误时用户误以为已生效。
- **不保留 alpha 通道**：SVT-AV1 编码器只支持 `yuv420p`/`yuv420p10le`，无法承载透明通道；
  当前样本（AI 生成图）均无 alpha，故不做 alpha 源图的路由分流。若将来出现透明源图且要求
  保留透明度，需按源图 alpha 分流回 ImageMagick（libheif 支持），判据可从图片 Meta 顺带取得。

## 实测基准

本机（Windows，16 核）用 4 张真实 ComfyUI 产物（1024–2304px 宽 PNG）实测，每个档位都拿
"前端档位对应的质量"作为 ImageMagick 基准（256w→q60、512w→q65、1024w→q70、2048w→q75，
即 webp 档位经 resolver 的 AVIF 再标定后的值）。

编码耗时（同图同档位对比，取 4 个样本的中位数。注意样本源宽度多为 768–1024px，
`scale='min(iw,N)'` 对不超过档位的源不放大，因此表中高档位对多数样本是原尺寸编码，
耗时不会随档位单调增长）：

| 目标宽度 | ImageMagick/libheif | ffmpeg/SVT-AV1（crf10） | 节省 |
|---|---|---|---|
| 256w | 330 ms | 252 ms | 78 ms |
| 512w | 452 ms | 328 ms | 124 ms |
| 1024w | 838 ms | 514 ms | 324 ms |
| 2048w | 822 ms | 446 ms | 376 ms |

单张最坏情况（2304px 宽的 `244-casual_winter` 缩小到 2048w）ffmpeg 1519ms vs magick 2618ms，
节省 1099 ms。

画质（对照 magick 缩放后的参考图算 PSNR，16 组对比）：ffmpeg 输出 16/16 组不低于
ImageMagick，其中 14/16 组高出 0.6dB 以上，最低仍高 0.14dB。

延迟构成（2304px 源输出 1024w）：传输约 23ms、服务端编码约 737ms、客户端解码约 117ms。
局域网传输仅占单张总延迟的 0.2%–3.2%，因此**优化目标是编码与解码耗时，不是体积**——
按体积百分比评估收益会得出错误结论。

magick 进程启动开销约 20–130ms，非瓶颈（消除启动的常驻进程方案只省 ≤0.1s，故未采用）。
