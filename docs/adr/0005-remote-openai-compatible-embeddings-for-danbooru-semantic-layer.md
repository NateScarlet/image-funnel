# ADR 0005: Danbooru 补全语义层依赖远程 OpenAI 兼容 embeddings 接口

## 状态

Accepted

## 背景

本地 Danbooru 补全原本只有**字面匹配**：分层打分（精确 > 中文别名精确 > 前缀 > 子串 >
模糊笔误容忍）。字面匹配对「记不准用哪个词」和「拼错」容错有限——用户记得语义大意却
说不出标签名时几乎无结果。

参考实现 [DanbooruSearchOnline](https://github.com/SuzumiyaAkizuki/DanbooruSearchOnline)
用**自包含模型**（sentence-transformers + torch）做语义匹配：把查询与标签编码成向量后
按余弦相似度召回。它作为线上服务给 MCP 用是可接受的，但不适合本地补全场景：

1. **推理成本与部署形态不匹配**。本地补全在 ComfyUI 提示词编辑时逐次触发，延迟预算
   在百毫秒量级；自包含模型默认落在 CPU 上，编码一条查询就是秒级。
2. **自包含模型要求用户额外部署一整套推理栈**（torch / sentence-transformers /
   模型权重），与「补全只是本地小工具」的定位不符。
3. **该服务准备新增用量限制**，把交互式本地补全挂在它上面等于把补全可用性交给别人的
   配额策略。
4. **模型与产品生命周期不同**。换嵌入模型是用户自己的事，不应要求改代码或重新拉取
   本项目的依赖。

## 决定

**语义层的查询向量与标签向量都走用户提供的 OpenAI 兼容 `/v1/embeddings` 接口，
项目不自包含模型、不引入推理框架。**

- 端点由 `HOOK_AUTOCOMPLETE_EMBEDDING_PROVIDER_URL` 指定，语法为
  `<base>#apiKey=<k>&model=<m>&timeoutMs=<ms>`；`apiKey` 为空时不发送 Authorization 头，
  默认指向本地 LM Studio。用户可指向任何 OpenAI 兼容实现（LM Studio、vLLM、Ollama、
  云网关），换模型只改 URL 里的 `model`。
- **标签向量在编译期生成**（见 `compile_danbooru_data.py`），与标签表一同落盘；运行时
  只读产物，不联网生成标签向量。
- 运行时用 **mmap** 映射向量产物，按**归一化矩阵暴力矩阵乘 + BLAS** 全量点积，精确
  召回，不引入 ANN 索引：5 万级规模下单次全表点积约 26ms，ANN 的复杂度与调参成本
  换不回这个量级。
- 语义层**仅在字面层没有任何强匹配时追加**，因此强命中路径完全不受嵌入服务可用性影响。
- 查询文本→向量走 **LRU 缓存**，连续输入同一查询不重复调用接口。
- 接口超时或失败时**跳过本次语义层**，返回字面结果并附一条错误提示项，补全不中断。
- 语义层激活需要**两个条件同时成立**：标签向量产物存在、嵌入服务 URL 非空。缺任一时
  语义层完全不工作，对未配置用户零行为变化。

## 后果

### 正面

- 模型选型与运行时解耦：换嵌入模型不需要改代码、不需要重新安装依赖。
- 不引入 torch 等重依赖，补全侧只多一个 `numpy`。
- 推理算力复用用户已有的 GPU 栈（LM Studio / vLLM），不在本机跑 CPU 推理。
- 离线使用：标签向量落盘后，语义召回的排序部分完全本地，只有查询编码需要可达端点。

### 负面

- **语义层有一个外部依赖**：端点不可达时降级为字面结果 + 错误提示。这是刻意的取舍——
  补全的可用性不能绑在推理服务的可用性上。
- **编译期需要端点在线**，且是长任务：实测 5.3 万标签 × 3 视图、批量 1024、CPU 侧
  LM Studio 约 48 分钟。批量生成一次请求要发送上千条文本，故编译脚本自带的默认端点带更长的
  超时（默认 60s），与交互式单条查询超时（默认 3s）是两套独立预算；URL 里显式指定的
  `timeoutMs` 一律优先，脚本不擅自覆盖。
- **查询延迟受端点影响**。端点是本地进程时，一次编码往返本身就是百毫秒到秒级；本项目
  只保证本地排序部分（字面两趟 + 三视图点积，重复查询实测约 76ms）落在百毫秒量级，
  不保证端到端交互延迟。端点越快，语义层体验越好；端点慢时它会退化为「字面结果 + 错误提示」。
- **向量产物常驻内存**（5.3 万标签 × 3 视图 × 1024 维 float32 ≈ 659MB，mmap 后按查询
  触碰全表，实际工作集接近此值）。逐查询重新映射并不省内存：实测每次重建映射的缺页
  开销约 271ms，是矩阵乘本身的十倍，因此映射常驻而非按查询开关。
- **常驻映射会占用产物文件**。Windows 下打开中的文件不可覆盖，重新编译标签向量前需要
  先退出补全进程；编译脚本对此给出明确提示。为避免留下「新标签表 + 旧向量」的行序错位
  产物，向量产物先于标签表落盘。
- **阈值需要按模型校准**。余弦相似度的绝对值随嵌入模型差异很大（同一批数据上，英文
  查询的强命中常在 0.75 以上，中文查询的强命中常在 0.65 上下）。换模型可能需要调整候选
  下限，否则表现为「语义层什么都不召回」或「召回噪声」。

### 被否决的替代

- **自包含模型（与参考实现相同）**：推理栈重、CPU 慢、模型生命周期与产品耦合（见背景 1~4）。
- **纯 CPU 本地推理**：单条编码秒级，远超补全延迟预算。
- **ANN 索引（HNSW/IVF）**：全量点积 26ms 已满足预算，ANN 引入额外依赖、召回率损失与
  参数调优，规模未到。
- **向量量化**：同上，且会改变相似度分布从而使阈值更难校准。
- **在线调用参考服务做查询向量**：把补全可用性交给第三方配额（背景 3）。
