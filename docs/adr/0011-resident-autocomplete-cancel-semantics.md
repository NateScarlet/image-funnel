
# ADR 0011: 常驻补全 `$/cancelRequest` 的取消语义

## 状态

Accepted

## 背景

JSON-RPC 常驻补全（`[directive.autocomplete].protocol = "json-rpc"`）由两侧各实现一半：Go 侧定义协议并管理常驻进程，Python 侧（`example_hooks/comfyui/autocomplete.py`）实现 `serve`。两侧对 `$/cancelRequest` 通知的理解不一致——Go 侧注释按「中断请求处理」设计，Python 侧只是标记后丢弃响应、计算继续跑完。此外 Python 侧以 `-32000` 上报脚本业务失败，Go 侧把错误码格式化进字符串后即丢弃，协议字段失去判别力。

## 决定

1. **`$/cancelRequest` 的语义 = 请求方不再需要该结果。** 接收方尽力尽早停止无谓工作，但**不承诺强制中断**；Go 侧不因取消而杀进程，Python 侧不保证打断任意阻塞调用，但必须尽力中止**在途 HTTP 请求**。
2. **在途 HTTP 真实中止。** Python 侧 serve 路径的网络调用改用可取消的同步客户端（httpx），收到取消时由另一线程关闭客户端，掐断在途连接。
3. **脚本错误码结构化保留。** Go 侧把 JSON-RPC error 的 `code` / `message` 保留为结构化类型，而不是拍平进错误字符串；当前不新增按码分支（无消费者需要区分）。

## 考虑过的选项

- **取消 = 真中断（协作式中断）。** 同步 `requests` 的阻塞调用无法从另一线程干净中断，给 Python 侧加「中断」契约会制造空头承诺，反而制造新的语义不一致。拒绝。
- **Go 侧取消时直接杀常驻进程。** 与常驻补全的初衷相悖——每次取消都丢进程并重新 spawn；且会误杀该进程上并发在途的其它请求。拒绝。
- **Python 侧整体异步化（asyncio + aiohttp/httpx）。** 最干净的协作式中断，但把一次缺陷修复变成架构迁移，代价与收益不成比例。拒绝。
- **维持「丢弃响应、不真中止」。** 用户明确要求已发出的网络请求可取消。拒绝。
- **给错误码加 Go 侧判别分支。** 当前唯一消费者是前端文本展示，没有任何行为会因错误种类改变；为不存在的消费者造类型属于过度设计，也为未来留下无意义的维护面。拒绝。

## 后果

- 取消语义在两侧一致，且由测试固定：Python 侧网络层单测（在途请求被掐断）+ serve 集成测试（取消信号传导到网络层）；Go 侧一条 typed error 单测（错误码可结构化断言）。
- Python 侧线程模型保留；补全与离线脚本共用的网络出口整体从 `requests` 换成 `httpx`（`example_hooks` 内不再依赖 `requests`），这些路径的功能行为不变。取消掐断的调用以独立于 `HttpError` 的错误上报，使「取消」不会被当作「失败」记日志或降级。
- 取消令牌挂在每请求载体上，网络层每次调用新建 `httpx.Client` 并把它注册为取消清理动作；令牌不能跨请求复用，因此语义层的共享缓存拆成「进程级共享矩阵 + 查询 LRU」与「请求级客户端」两半。这是令牌作用域的后果，召回结果不变。
- 未来读到取消逻辑的人不应把它当作「未真正中断」的 bug 去「修复」——不承诺中断是本 ADR 的有意取舍，要改需先推翻本 ADR。
