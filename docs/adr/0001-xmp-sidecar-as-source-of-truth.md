# XMP Sidecar 作为图片元数据的唯一持久化来源

选择 XMP 配套文件而非数据库或直接修改原始图片来存储评分、标签和筛选操作结果，使得元数据对专业图片管理工具透明可读，且原始文件永不损坏。

## 考虑过的方案

- **修改原始图片 EXIF/IPTC** — 有损操作，可能损坏 AI 生成的图片（部分生成器写入的非标准元数据字段可能被覆盖）；不同图片格式的 EXIF 支持不一致（如 WebP 的 EXIF 支持有限）。
- **嵌入式数据库（SQLite 等）** — 元数据与图片文件分离，移动/复制/备份图片时元数据不会跟随；需要额外的数据库维护和备份策略；跨设备同步需额外方案。
- **关系型数据库（PostgreSQL 等）** — 单机场景下过度设计，与 SQLite 相同的元数据分离问题，且引入了外部服务依赖。

## 结果

- 允许 Adobe Lightroom/Bridge、XnView 等专业工具直接读取评分，无需专属导出步骤。
- 元数据与图片共存于同一目录，移动/复制/整理时自动跟随。
- 零数据库运维负担——整个应用可以装在一个 U 盘里运行。
- XMP 解析和生成引入了有限的外部依赖（`xmp-go` 库），但 XMP 本质是标准化的 XML，即使库出现问题也可降级为手动解析。
- 元数据查询能力受限（无法执行跨目录的复杂聚合查询），但当前筛选场景以单目录为单位操作，不属于问题。
- 文件监听和并发写入需额外防护（XMP 文件可能被多个进程同时读写），但此问题存在于所有 filesystem-based 方案中，非 XMP 特有。
